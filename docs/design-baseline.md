## 1. 总览

### 1.1 产品是什么

**产品是什么**：手机（H5）上说一句大白话 → 系统生成策略并回测 → **每天自动帮你跑一遍**，
用未来真实发生的数据验证这个想法靠不靠谱。不做实盘，只做研究。

**为什么这个位置值得做**：竞品都在往中间挤（问财加自然语言回测、果仁加社区与实盘、
PandaAI 加 App 与课程），但没人把「手机上、大白话、只做研究、**并且承认策略需要时间证明**」
这条链路做扎实。窗口期约 6–12 个月。

### 1.2 系统结构（六层）

```
① 客户端     H5 纯 Web（唯一客户端，后续 PWA 加主屏）
② API 网关   FastAPI：意图解析 / 策略提交 / 任务查询 / 结果 / 资产目录   ← 缺鉴权限流
③ 业务编排   任务状态机 · 异步执行 · 重试修复 · 结果落库 · 策略日更跟踪   ← 内存实现
④ 核心能力   AI 生成层(A/B/C) · 数据工坊 · 模型工坊
⑤ 沙箱执行   podman(--network=none) + qlib + AST 守卫 + 标准化结果
⑥ 基础设施   PostgreSQL · Redis · MinIO · NAS(行情)
横切：测试 · 可观测 · 安全合规    旁挂：Admin 运营后台（Phase 1.5）
```

| 层 | 关键模块 | 状态 |
|---|---|---|
| ① 客户端 | `quantpilot-h5/`（原生 JS，零构建） | 三入口完成；无登录 |
| ② API | `app/api/app.py`、`deps.py` | 接口齐全；**鉴权/限流缺** |
| ③ 编排 | `app/orchestration/task_service.py`、`app/tracking/` | 骨架有；**内存、无队列、无调度器** |
| ④ 能力 | `app/services/llm/`、`app/services/intent/`、`app/data/`、`app/models/` | 意图层与数据工坊完整；模型工坊只有注册表 |
| ⑤ 执行 | `sandbox/`、`app/services/executor/` | 设计完整；环境不稳（machine 不自启） |
| ⑥ 基础 | `app/db/`、`scripts/pg.sh`、NAS | PG 接资产域与 Track；**Redis/MinIO 缺** |

**核心调用链**（一次性）：

```
POST /strategies {intent}
 → Stage A：意图 → StrategySpec（Pydantic 校验失败回填重试）
 → Stage B：Spec → Python 代码（AST 白名单 + 固定区比对，失败修复重试）
 → Stage C：执行失败 → LLM 修复（最多 N 轮）
 → 沙箱执行 → QUANTPLOT_RESULT:{json} → 结果校验 → 落库
 → GET /tasks/{id} → 前端渲染
```

**第二条链路**（长期存活）：见 §4——日更只跑信号与记账，不重跑回测。

**四个内置资产域**：

| 域 | 内容 | 状态 |
|---|---|---|
| 数据工坊 | 因子/数据集/血缘/PIT/质量门禁 + CSV 导入审核（uploaded→pending_review→approved→published） | 后端完整，无 UI |
| 模型工坊 | 注册表 + 基准评测契约（PromotionRule）+ beta→active | 只有注册表，**无评测执行器** |
| 提示词 | Stage A/B/C 三段式；表达式写法与算子白名单单一数据源 `prompts/operators.yaml` | 完整 |
| 资产状态机 | `draft → validating → active/deprecated` | 代码对齐，Admin 未做 |

### 1.3 现在的真实状态

单点技术比同类早期产品扎实（契约、AST 守卫、断网沙箱），但产品面长期只有一个"一次性回测"，
且那个回测的真实性还没被完全证实。

| 维度 | 状态 |
|---|---|
| 零代码交互（三层入口 + 确认卡） | ✅ 已落地（11-24） |
| 策略观察期后端骨架（Track 六表 + 12 接口） | ✅ 已落地（11-24），真实行情未接 |
| 真实回测链路 | ⚠️ 11-23 跑通过一次；当前机器 podman machine 未启动 |
| 回测真实性（T+1/涨跌停/停牌/滑点） | ❌ Track 侧已实现，**首次回测侧缺** |
| 任务持久化 + 队列 | ❌ 仍全内存，重启即丢 |
| 鉴权 + 限流 + 成本闸 | ❌ 零实现（key 与算力对公网裸奔） |
| 因子/模型绩效 | ❌ 是手写先验值，不是算出来的 |
| 测试 | ✅ 160 个离线全绿；**无真实回测的集成测试** |

## 2. 产品定位与边界

### 2.1 目标用户

不懂量化、不会写代码、有手机、想验证一个选股想法的人（画像 A）。
不是给专业研究员做工具——那是聚宽/米筐的战场。

### 2.2 唯一原则

**用户说的话永远是"人话"，表达式只允许存在于后台内部。**

任何界面不得要求用户写公式、填表达式、选算子、看代码、懂 IC/IR/Alpha158。
专家细节可以存在，但默认折叠，且不影响主流程。

### 2.3 能力诚实边界

当前数据只有**日频量价**（open/high/low/close/volume/amount/vwap/factor），
所以后台能稳定接住的想法只有五类：

| 用户说法 | 后台映射 | 状态 |
|---|---|---|
| 涨得猛的 / 追涨 / 强者恒强 | 20 日动量 | ✅ |
| 跌多了的 / 抄底 / 超跌反弹 | 5 日反转 | ✅ |
| 稳一点 / 波动小的 / 别大起大落 | 20 日低波 | ✅ |
| 有量的 / 活跃的 / 放量的 | 量比 | ✅ |
| 便宜的 / 低位的 | **价格低位代理**（相对一年均价），不是真估值 | ⚠️ 近似，必须说明 |
| 好公司 / ROE 高 / 盈利好 | 需要财务数据 | ❌ 明确告知做不到 |
| 北向资金 / 龙虎榜 / 新闻情绪 | 需要另类数据 | ❌ 明确告知做不到 |

**做不到就说做不到，不许用相近的东西糊弄。** 唯一例外是"便宜→价格低位"，
因为语义接近，但必须在假设里写明"这里用的是价格位置，不是市盈率"。

### 2.4 明确不做的事

| 别做 | 原因 |
|---|---|
| 数据广度军备竞赛 | 拼不过东财/PandaAI 的数据团队；先用好日频量价 + 少量特色因子 |
| 多 Agent 研究工作流 | 那是 PandaAI EVO 的战场，一条能跑通的单链路更有价值 |
| 实盘 / 券商对接 | 合规成本极高，与"模拟盘起步"的定位冲突 |
| 专业指标堆砌 | 目标用户不懂量化，指标越多越劝退 |
| 原生 App / 小程序 | 已定用 H5（PWA）替代，规划里不带原生端 |

## 3. 零代码架构（Intent Layer）

### 3.1 三层入口，同一套后台

```
① 模板卡（0 认知）   点「追涨」「抄底」「稳健」→ 直接出结果
② 向导三问（半结构） 从哪选 → 想要什么 → 多久换一次 → 出结果
③ 一句话（自由）     "帮我找便宜又稳的，每月换一次"
        ↓ 三者都收敛为同一个结构
                 IntentFrame
        ↓ RecipeCompiler（确定性，无 LLM）
              StrategySpec → 代码 → 沙箱 → 结果
```

**关键**：三个入口产出同一个 `IntentFrame`，后台只有一条链路。
引导式不是另做一套逻辑，而是"替用户填 IntentFrame"。

### 3.2 语义层：IntentFrame

LLM 只负责一件事——把中文变成下面这个结构，**绝不输出表达式、代码、字段名**：

```jsonc
{
  "universe": "csi300",          // csi300 | csi500 | csi1000 | all | null
  "styles": ["momentum"],        // 只能从固定枚举里选
  "topk": 20,                    // null = 没提
  "rebalance": "month",          // day | week | month | null
  "risk_level": "balanced",      // conservative | balanced | aggressive | null
  "need_model": false,
  "restated": "在沪深300里挑最近涨得最猛的20只，每月换一次",
  "confidence": 0.86,
  "missing": []
}
```

`restated` 是用户唯一会看到的"理解结果"——一句人话复述，不是 JSON。

**为什么不让 LLM 直接写 Spec**：Spec 有 9 条跨字段校验 + 算子白名单，让 LLM 一次全对是赌博；
而"从 6 个风格里选 1–2 个"是分类任务，准确率高一个数量级。
**把不确定性关在语义层，把确定性交给编译器。** 表达式只出现在 `app/services/intent/recipes.py` 一处。

### 3.3 澄清机制（永远不让用户卡住）

1. 缺**标的池** → 给选项但**不阻塞**，默认沪深300 + 写进假设
2. 缺**风格**（或风格冲突）→ 必须问，给 4 个选项，各配一句人话
3. 缺 topk / 频率 / 风控 → **不问**，用默认值 + 写进"我替你做的假设"
4. `confidence < 0.6` → 把 restated 给用户确认，而不是直接跑

问题形态固定为**选择题**（含推荐项），一次最多 2 题，绝不开放式追问"请详细描述"。

### 3.4 透明 ≠ 让用户配置

跑之前展示一张"我理解成了这样"的卡片：

```
标的      沪深300
挑什么    最近 20 天涨得最猛的
买多少    20 只（你没说，我按 20 只）
多久换    每月第一个交易日
风控      单只不超过 10%
```

下面一行小字：`AI 替你做了 3 个默认选择，点这里改`。默认值直接生效，想改才展开。

### 3.5 用户永远看不到的东西

表达式 · Python 代码 · 算子白名单 · AST 校验 · 沙箱 / 容器 / 镜像 · 训练集验证集切分 ·
Alpha158 · IC/IR · qlib · TopkDropout · 执行日志路径

这些全部留在后台，只以"我们做了安全检查""模型在学习规律"这类人话出现。

### 3.6 失败不许静默

后端回测失败或连不上时，结果页顶部必须出现横幅，且**说清原因**：

| 真实原因 | 界面文案 |
|---|---|
| 执行环境不可用 | 回测服务在这台机器上没跑起来（执行环境不可用） |
| 轮询超时 | 等太久了，任务可能卡住了 |
| 网络不通 | 后端没有连上 |
| 预置历史条目 | 本地演示数据 |

技术原文只进 console。**任何情况下都不允许把 mock 结果当真实回测展示。**

### 3.7 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/intents/parse` | 一句话 → frame + 中文参数卡 + 澄清问题 + 假设（响应不含任何表达式） |
| POST | `/api/v1/strategies` | 提交 `intent`（自由）或 `frame`（引导式已确认，走确定性编译不调 LLM） |

## 4. 策略观察期（Track）

### 4.1 为什么回测不够

两条不同的时间线，不能混：

| 要确认什么 | 靠什么 | 需要多久 |
|---|---|---|
| 系统有没有理解对我的想法 | 确认卡复述 + 可改参数 | 当场 |
| **这个策略到底有没有效** | **前向样本**（上线后才产生的数据） | 不可压缩，以周/月计 |

回测只能证明"这个想法在历史上说得通"，不能证明"它明天还行"。
**唯一可信的证据是前向天数**——所以策略必须每天跑，直到用户放弃或得出结论。

### 4.2 三个对象

```
Strategy（策略，不可变版本）
   │  spec + params 冻结后不可改；改 = 新 version
   ├── BacktestRun（首次回测，一次性，历史固化，永不重算）
   └── Track（观察实例，长期存活）★ 核心聚合根
          ├── Signal（每日目标组合）
          ├── Position（每日纸面持仓）
          ├── Nav（净值 / 基准 / 超额 / 换手 / 费用）
          ├── Event（时间轴日志 = journal）
          └── Checkpoint（检查点 + 证据等级 + 判定）
```

**关键约束**：Track 一旦创建，`spec` 与参数**只读**。想改 → `fork` 出新 Track，老的继续跑到检查点。
这不是限制而是亮点：**天然形成 A/B 对照**，且保住老 Track 的样本外纯度。

### 4.3 每天跑什么：信号，不是回测

**跑今天的信号和今天的账，不跑历史。** 回测已固化，数据没修订就永远不需要重算。

一天的真实时序（A 股，收盘后）：

| 时间 | 阶段 | 做什么 | 耗时 |
|---|---|---|---|
| 15:05 | T0 数据 | 增量拉当日行情、复权因子、停牌、涨跌停、指数 | 1–3 min |
| 15:20 | T1 因子 | **一次**算全市场当日截面（所有 Track 共享） | 1–3 min |
| 15:25 | T2 信号 | 按 Track 扇出：打分 → 排序 → topk → 目标权重 | N×10ms，1000 个 < 30s |
| 15:30 | T3 记账 | 目标 vs 昨日持仓 diff → 撮合 → 净值点 | 同上 |
| 15:35 | T4 评估 | 命中检查点？触发失效线？更新证据等级 | 秒级 |
| 15:40 | T5 通知 | 站内红点 / PWA 通知 / 周报排队 | — |

> **成本关键**：因子截面只算一次，成本与 Track 数量无关；扇出只做组合层（排序取 topk），纯内存运算。
> **日更 LLM 调用次数 = 0**——全是确定性计算，LLM 只在首次生成和周报文案用。

### 4.4 记账硬约束（决定结果可不可信）

纸面跟踪最容易造假，必须写死：

- **T+1**：当日信号次日**开盘**成交，不允许当日买当日卖
- **涨停不可买 / 跌停不可卖**：记录 `unfilled_reason`，权重留给现金
- **停牌不可交易**：持仓按停牌前价挂账，标注
- **费用**：佣金万 2.5 + 印花税千 1（卖出）+ 滑点（默认双边 10bp）
- **现金账户**：未买满留现金，不假装满仓（显著影响净值，必须显式）
- **数据快照绑定**：净值点记 `data_snapshot_id`；行情修订时**不重写历史净值**，只追加修正事件

### 4.5 两条执行路径（重要架构决策）

现有系统只有"沙箱跑代码"一条路，日更用它太重（1000 个策略 → 1000 个容器/天不现实）：

| 路径 | 适用 | 执行方式 | 单次耗时 | 能否日更 |
|---|---|---|---|---|
| **A 声明式** | 零代码 frame 编译出的 spec（主路径） | 进程内向量化求值器 | 10 ms–1 s | ✅ 可批量 |
| **B 代码式** | LLM 生成的 Python | podman 沙箱 + AST 守卫 | 1–5 min | ⚠️ 限量配额 |

B 路径只用于首次回测，不默认进日更；用户要日更则引导"A 路径等价表达"。

### 4.6 判定：上线即锁定规则（pre-registration）

创建 Track 时把规则写进 `rules_json`，之后只读——防"天天来问还行吗"和事后诸葛亮：

| 项 | 默认值 | 可改 |
|---|---|---|
| 观察窗口 `horizon` | `max(20, 3 × 调仓周期)`：日 20 / 周 30 / 月 90 交易日 | 上线前 |
| 失效线 | 20 日超额 < −8%，或连续 10 日空仓，或信号连续 5 日无变化 | 锁定 |
| 达标线 | **不设收益目标**，只看"是否按设计工作" | 锁定 |
| 检查点 | 7 日（体检）/ 20 日（初步结论）/ 60 日（可信结论） | 锁定 |

> 为什么不设"赚 10% 算成功"：那是承诺收益，既不合规也不诚实。**我们承诺验证过程，不承诺结果。**

**证据分级**：

| 等级 | 条件 | 一句话 |
|---|---|---|
| L0 | 只有回测 | 历史上说得通，值得盯 20 天看看 |
| L1 | 影子 ≥ 20 日 | 回放这 20 天没崩，但不算数 |
| L2 | 真实前向 ≥ 20 日 | 真跑了 20 天，方向对得上，样本还少 |
| L3 | 真实前向 ≥ 60 日且偏离回测 < 阈值 | 跑了 60 天，和回测预期基本一致 |

**永远不说"这个策略有效"**，只说"到目前为止，证据到哪一级"。

判定必须带归因，三种之一：**按设计工作** / **没跑起来**（bug 或数据问题，不是策略问题）/ **跑起来了但偏离**（选股偏差 / 成交摩擦 / 风格切换）。

### 4.7 影子回填（不让用户干等）

上线时用历史回放到今天，生成"假如你那天上线"的曲线（最多 60 日）。但必须：

1. **虚线 + 灰底 + 「回放」角标**，与真实段严格视觉隔离
2. **不参与判定**——用户已看过全样本，这段仍受隐性过拟合污染
3. 文案明说"这是回放的，不算真实成绩"

### 4.8 生命周期与配额

| 方式 | 触发 | 数据处理 | 可恢复 |
|---|---|---|---|
| `concluded` | 到 20/60 日 | 冻结，保留全部 | 可继续观察到 60 日 |
| `abandoned` | 用户主动放弃 | 保留 90 天后软删 | 90 天内可复活 |
| `auto_paused` | 连续异常 / 数据缺失 | 停在异常前一日 | 修好后 resume，缺口标记 |
| `archived` | 沉默 30 天无访问 | 停止日更，降为冷存储 | 一键复活 |

**沉默用户是最大流失来源**，所以不做"到期自动删除"，做"冷归档 + 一键复活"。

配额：免费 3 个并发观察，付费 10–20 个。理由不是算力，是**注意力**——观察 20 个等于没观察。

**fork 即 A/B**：用户改参数 → 不动老 Track，新建一条并排跑。
文案：*"你改的这一版我另开了一条，老的那条继续跑。20 天后你有两组真实数据可以比，比拍脑袋靠谱。"*

### 4.9 前端交互（Track 上线后）

| 页面 | 现在 | 目标 |
|---|---|---|
| 首页 | 「说一句大白话做策略」输入框 | 输入框 + **「我在观察的」卡片流**（今日信号 / 累计超额 / 状态灯 / 下次结论日期） |
| 确认卡 | 复述 + 参数 + 假设 | 底部加一行「我会怎么验证你」：回放 20 天 + 每天 15:40 出信号 + 满 20 个交易日给初步结论 |
| 结果页 | 一次性指标卡 | **Track 详情**：journal 时间轴（左）+ 净值 vs 基准（右）+ 每日持仓变化 + 偏离诊断 |
| 通知 | 无 | 每日一句话；失效线触发高优推送；每周一份周报 |

**文案示例**（这些决定了产品的"诚实感"）：

- 上线：*"好了，从明天开始我每天收盘后帮你跑一遍。满 20 个交易日（大概 12 月 22 号）我给你第一个结论。中间你要是想停，随时说。"*
- 第 7 天：*"跑了一周。今天选了 5 只，有 1 只涨停没买进。累计 +1.2%，同期大盘 +0.8%。还看不出啥，继续。"*
- 第 20 天：*"满 20 天，第一份结论：方向对得上，但成交比回测差一点（涨停买不进）。证据等级：初步。"*
- 失效：*"这个想法最近 20 天跑输大盘 9 个点，超过了我当初跟你定的线。建议先停掉，要不要看看是哪里走偏了？"*

## 5. 存储与数据构建

### 5.1 结论先行

**PG 是最优解，但它只该管元数据与用户；行情不该进 PG，也不该现在引入列式数据库。**
**qlib binary 是引擎读取格式，不是数据存储格式——它可以"读"，不能当"真源"。**

### 5.2 按负载拆开看

| 负载 | 特征 | 该用什么 |
|---|---|---|
| 用户 / 会话 / 额度账本 | 单行读写、强一致、唯一约束 | **PostgreSQL** |
| 任务 / 回测记录 / Track 账本 | 状态机流转、按用户翻页 | **PostgreSQL** |
| 任务队列 / 限流 / 缓存 | 高频计数、TTL | **Redis**（`INCR`+`EXPIRE`，不是 PG 计数） |
| 回测引擎读行情 | 单股时间序列、顺序扫描 | **qlib binary** |
| 横截面分析 / 因子回填 / 质检 | 扫多列、聚合、排序 | **Parquet + DuckDB** |
| 分钟线 / 十年 tick / 高并发 | 十亿行 | **ClickHouse**（不是现在） |
| 大结果 / 日志 / 生成代码 | 大对象 | MinIO |

### 5.3 为什么不把行情塞进通用数据库

qlib 官方 README 基准（800 只股票 2007–2020 日线，构造 14 因子数据集，单 CPU）：

| 存储 | 耗时 |
|---|---|
| Qlib binary + ExpressionCache + DatasetCache | **7.4 s** |
| Qlib binary（无缓存） | 47.6 s |
| HDF5 | 184 s |
| MongoDB | 253 s |
| MySQL | 365 s |
| InfluxDB | 368 s |

官方结论：通用数据库要经过太多层接口和格式转换，反而拖慢加载，qlib 紧凑格式才是为科学计算数组准备的。

**推论**：任何"把 K 线搬进 PG/ClickHouse/InfluxDB 让回测更快"的方案，方向都是错的。
正确做法是**引擎继续吃 binary，另外派生一份 Parquet 给分析用**——两份数据、两个用途。

### 5.4 为什么 qlib binary 不能当真源

现有数据是 chenditc/investment_data 的每日发布包（qlib 兼容格式）：
**6177 只股票 × 10 字段 ≈ 6.2 万个 `.bin` 小文件**，6514 个交易日。

它有三个装不下的东西，恰好全是 Track 记账的硬依赖：

| 缺什么 | 后果 | 能否推导 |
|---|---|---|
| **停牌标记** | qlib 里停牌与缺数据**都是 NaN**，两者无法区分。停牌应"持仓不动、按停牌前价估值"，缺数据应"报 gap 并停跑"——混淆会把管道故障伪装成正常净值 | 只能猜（`volume==0`），猜不开 |
| **涨跌停价** | `change` 只说"涨了 9.8%"，不说涨停是 10% 还是 20%。主板/创业板/科创板/北交所/ST 五套限幅 | 可用 `prev_close × 系数` 算，但**系数要外部给**（板块 + ST 状态） |
| **快照版本** | 一个日期一个值，覆写即丢历史 | 不能 |

**更根本的**：`dump_bin.py --update 1` 只把新日期追加到 `.bin` 尾部，**历史永不回补**。
上游修正了 2019 年某个价格，binary 里永远是错的旧值，且没有任何机制告诉你它变了。
观察期净值需要可追溯，而它会静默漂移——这就是它不能当唯一真源的决定性理由。

### 5.5 三层数据架构

```
L0 落地区（Parquet，唯一真源，只追加）
     原始价 / 成交量 / 停牌标记 / 板块 / ST 状态 / 成分股变动
     按 trade_date 分区，每天一个文件，永不改写
        │
        ├──→ L1 引擎层：dump 成 qlib binary  ── 回测读（7.4s）
        └──→ L2 分析层：Parquet + DuckDB     ── 横截面/因子/质检
```

**方向永远是 L0 → qlib，不能反向。** qlib 丢了能重建（从 L0 重刷）；L0 丢了就是真丢。
如果让 qlib 当源头，你**永远补不进停牌表和 ST 历史**——因为它们无处安放。

落地要点：
1. 现有 `sandbox/data/cn_data` 留着别动，它就是 L1，继续能跑回测
2. **只补一张很小的表**：`trade_date × symbol → suspended / limit_up / limit_down / board / is_st`。
   日更只需当日全市场快照（6177 行/天，一年 150 万行）
3. **涨跌停价可以不存**，用 `prev_close × 系数` 现算，只存板块和 ST 状态
4. **停牌可以不存**，用"当日无快照"表示（前提是 L0 每天全量落一份）
5. **L0 从第一天就只追加不改写**。这条现在不做，以后补不回来

### 5.6 体量与阶段

| 数据 | 行数 | 原始 | Parquet(zstd) | 结论 |
|---|---|---|---|---|
| 日线 20 年 | ~3000 万 | ~1.5 GB | 300–500 MB | PG 也装得下，但聚合慢 10–50× |
| 分钟线 1 年 | ~3.6 亿 | ~17 GB | 3–5 GB | 列式主场 |
| 分钟线 5 年 | ~18 亿 | ~86 GB | 15–25 GB | 必须列式 |

阶段路线：**现在** PG + Redis + qlib binary（不加数据库）→ **Phase 2** 加 DuckDB（是库不是服务）→
**Phase 3** 满足任一条件才上 ClickHouse（接分钟线 / 并发撑不住 / 需对外 SQL 接口）。

> 关于 Rust 列式库：GreptimeDB / InfluxDB 3 / Databend 确实存在，但最佳场景分别是可观测性指标、
> metrics、云数仓，都不是"股票横截面研究"。**"Rust 写的"不等于快**——快的来源是 Arrow 列存、
> 向量化执行、谓词下推，这些跟语言无关，用 Polars/DataFusion 这个库形态更划算。
> `pg_analytics`（2025-03 归档）、`pg_mooncake`（被收购后停更）、Hydra Columnar（2024-04 停更）都不能选。

### 5.7 一个现实警告

现在 `prepare_data.sh` 是**下整包 tarball 解压覆盖**（chenditc 每日发版）。
意味着日更 Track 的真实成本是"每天重下 GB 级包 + 全盘替换 6.2 万个小文件"，
而不是"追加 6177 行"。**Phase 1 能忍，一旦 Track 每天跑，它就是第一个瓶颈。**
且 6.2 万个小文件放 NAS 上，元数据操作本身会拖慢冷启动。

### 5.8 本地开发环境

PG 用 podman 跑，不用装本机数据库——这是刻意的：**开发环境与生产环境同一套容器定义**，
避免"我这能跑你那儿不行"。数据落命名卷而不是绑 Windows 目录，因为 PG 初始化要
`chmod 700`，virtiofs 不认 POSIX 权限，绑过去必然启动失败。

具体命令、参数与排错见 `DEPLOYMENT.md` §5。

## 8. 风险清单

| 风险 | 后果 | 对策 |
|---|---|---|
| 用户把影子回填当实盘成绩 | 信任崩塌 | 虚线+灰底+角标，文案隔离，不进判定 |
